Grounding Context

Codebase Context

  • Mac (personal repo). Almost nothing: session.sh (an fzf picker giving one tmux session per project) and notes.sh. No awareness of what agents are doing, no task store.
  • Ubuntu (work dotfiles): the wb workbench. About 16k lines of bash (wb.sh ~6.2k), about 50 test files, about 110 PRs and about 30 skills. Each task gets one tmux session, one git worktree and one markdown task file. The task store, ~/code/tasks, holds about 360 files with Plan / Handoffs / Decisions / Done / Follow-ups sections, per-task locks, parent/child families, a decision-capture shelf and a weekly review. The direction set on 2026-10-17 is to delete features, then have Go own reading and writing the task store.
  • Most-used loops: /wb-resume 91 and /wb-save 86 transcripts, /decision-buffer 56, /handoff 27, /close-out 19. Weekly review has run once. Several skills have never been used.
  • Known fragile spots. Status is half hooks, half scraping of pane titles and modals ("this pair of greps is the one thing to recalibrate"). Handoff types into panes with send-keys; the first Enter is sometimes dropped and the permission menu is answered by sending '2'. About 30 Linux-only dependencies. Task status values have drifted from the schema. Planned tasks outnumber doing tasks 183 to 22.
  • Boundary. Employer content never lands in personal surfaces. The task store has no remote, and the boundary rule is "deliberately the last decision". A single dotfiles repo for both machines forces that decision.

External Context

  • Claude Code now covers part of what wb builds by hand (checked against code.claude.com):
    • Messaging between sessions: ListAgents/SendMessage over a per-session socket, with notify_when_idle. Hooks and scripts get the socket, so they can post into a session.
    • Agent view: claude agents shows each session as Working / Needs input / Idle / Completed. Sessions can run in the background with --bg or /bg.
    • Remote Control: reach a local session from your phone.
    • Agent teams (experimental): a shared task list plus a mailbox per teammate.
  • Agent-oriented trackers: beads (a git-backed dependency graph with bd ready and compaction of old work) and Backlog.md (markdown task files kept in the repo).
  • Hook-driven status tools (cekanje, CCN, ntfy Stop-hook scripts) each independently rebuilt the same status layer wb has.
  • Third-party orchestrators come and go: Vibe Kanban's company shut down in April 2026, and Crystal became Nimbalyst. That argues for keeping your own layer thin.

Topic Axes

  1. Session lifecycle: start, switch, pause, save/resume, wind down

  3. Coordination between sessions: handoff, messaging a live agent, fan-out

  5. Cross-machine, boundary and upkeep: Mac/Ubuntu parity, personal/employer split, cost of maintaining the tooling

1. The Mac as a native-only control arm

Idea 1Axis 5 · Cross-machine & upkeepConfidence 85%Complexity Low
Description
The Mac has none of wb, so use it as a free experiment. For two or three weeks, run it on Claude Code's native features only (agent view, --bg, messaging between sessions, Remote Control, worktrees, named resume) plus an off-the-shelf tracker such as Backlog.md or beads. Keep a short "missed it" log, and score each wb feature as native covers it, keep or retire. Port to the shared repo only what the log shows is missing, and give tooling PRs an explicit budget.
Basis
  • direct: the Mac has only session.sh and notes.sh; the wb port was kept out of the convergence plan; about 40 October PRs went to the tooling itself; several skills have zero uses.
  • direct: the current-state doc says the native overlap "has not been checked against what wb hand-builds".
  • external: the verifier confirmed agent view (with a Needs input state), --bg and ListAgents/SendMessage exist.
Rationale
Porting first copies features before anyone knows which ones the platform made redundant. A clean machine is the only cheap place to measure that, and the answer reshapes every other idea here, including how much of the Go port is still needed.
Downsides
Personal Mac work differs from work-machine work (fewer parallel tasks, no Jira), so the experiment undercounts some needs. Several native features are research previews and may change under you.

2. Native messaging replaces send-keys; fan-out becomes compiled "parts"

Idea 2Axis 3 · CoordinationConfidence 75%Complexity Medium
Description
Keep the handoff convention, where the task file is the payload and the message is a pointer to it. Deliver the pointer with Claude Code's SendMessage instead of typing into a pane: no boot regex, no resent Enter, no '2' keystroke for the permission menu. send-keys is only for booting a brand-new session. Once delivery is reliable, fan-out is cheap. A family's plan and CONCEPTS.md compile into one "part" per child: its slice of the plan, its first action, the files owned by its siblings (hands off), and where to report back. Each part goes as a message.
Basis
  • direct: handoff.sh:393-400 "The very first Enter ... can be silently dropped — observed live"; :410-412 answers the permission menu by sending '2'; roadmap-handoff.md:176-194 says this class of bug can't be caught in tests.
  • direct: handoff-guide.md:71-87 lists fan-out, instructing a busy agent and non-blocking handoff as non-goals.
  • external: native messaging uses a per-session socket that a busy receiver reads between tool calls; hooks and scripts get the socket.
Rationale
Handoff is used often (27 transcripts) and is the most fragile mechanism in the system. Replacing its delivery path removes a bug class that can't be tested, makes three listed non-goals reachable at once, and behaves the same on both OSes.
Downsides
Native delivery starts a turn on an idle receiver. That is close to the "idle-triggered delivery" the queue plan explicitly rejected, so you need to decide whether that rejection still holds. Messages from another Claude can't grant permission, so a spawned agent's first permission prompt still needs you.

3. Implicit checkpoints and an evening screening

Idea 3Axis 1 · Session lifecycleConfidence 75%Complexity Medium
Description
Two moves on one primitive:
  • Checkpoints. A Stop / PreCompact / SessionEnd hook uses a cheap model to write a draft handoff onto the shelf. /clear or exit is the trigger, and you are the one who does it, so the block on agents clearing themselves never applies. /wb-save and /wb-resume become escape hatches rather than rituals.
  • Evening screening. At the end of the day, one "screening" pass walks every live session: its diff since morning, a short digest and the drafted handoff. Accepting a draft records it and closes that session cleanly. The morning step rebuilds sessions from the store.
Save, review and wind-down all become one sitting.
Basis
  • direct: wb-save.md:8-11 says an agent clearing its own context was hard-blocked; usage is 91 and 86 for resume and save; implicit save is "planned, not built" (where-we-are.md:176-182).
  • direct: capture-nudge plan :31-33: "38 nudges fired and 3 were genuinely followed ... accepted 10 times out of 12" when a person reviewed the draft; one session accepted 5 of 7 drafts in under two minutes.
  • direct: the original shutdown scope, "sweep every live session, capture a quick status into each task file ... then close all sessions cleanly", never shipped (roadmap-day-bookends.md:31-33).
Rationale
The two most-used skills are rituals around one keystroke. Your own data says drafts reviewed in a batch work and prompts mid-task don't. Combining them removes about 177 manual invocations and finishes the day-bookends thread with the same mechanism.
Downsides
Implicit save is already on the roadmap, so the new part is the screening. A cheap model can write a weaker handoff than a deliberate /wb-save. The screening needs to stay quick or it becomes the next ceremony that never gets run.

4. Realms: the boundary decided by location, not by a rule

Idea 4Axis 5 · Cross-machine & boundaryConfidence 70%Complexity Medium
Description
The shared dotfiles carry only tooling and generic skills. Every command resolves a realm from the git remote of the working directory, the same way includeIf picks your git identity: employer org → work realm, JetNoLi/* or non-code → personal realm. Each realm has its own store root, and only the personal one may have a remote. A hook refuses any write, recall or handoff that would cross realms. Employer-specific settings, the plugin marketplaces and wb's work-only parts live in a per-machine overlay (convergence option c). Two variants worth weighing:
  • The record lives in the repo it's about, so git ownership is the classification.
  • The employer's tracker holds the durable record for work tasks, and the local store is only expiring scratch.
Learning-os and other personal long-running projects then become a personal-realm family instead of a second system.
Basis
  • direct: limitations.md:42-49 calls the boundary rule "deliberately the last decision", with "the task store gets no remote" as the interim guard.
  • direct: claude/README.md:44-50: settings.json mixes machine-local state with employer plugin marketplaces.
  • direct: the convergence findings list options (a) personal base, (b) work repo, (c) base plus overlay, and plan git identity through includeIf.
Rationale
Merging the repos makes the deferred decision unavoidable. Deciding by location gives a mechanical check instead of relying on you to remember a rule. It also lets the personal side sync across both machines while work content stays unsyncable.
Downsides
Tasks that span realms (a personal tool used at work) need a convention. The record-in-repo variant breaks families that span several repos. The employer-tracker variant ties the workflow to Jira.

5. Off-terminal paging on native state

Idea 5Axis 2 · Awareness & attentionConfidence 70%Complexity Low
Description
Turn "glance at the status bar" into "get paged only when you're the bottleneck". Needs-input events, and finished turns over 30 seconds, push to the phone or desktop (ntfy, macOS notifications, notify-send). They are deduplicated and acknowledged when you focus the pane. The payload carries no content, only something like "ubuntu · slot 3 · needs input", so nothing employer-related leaves the machine. Tapping opens Remote Control. Read status from native state (hooks and agent view) first. A hook-fed event log is the fallback only if that proves insufficient, and then the title and modal scraping gets deleted.
Basis
  • direct: attention reaches you only through tmux status-left and prefix+j/J, so nothing reaches you away from the terminal.
  • direct: tmux.conf:125-128 "focus = acknowledged" and DONE_MIN_SECS=30 already encode paging rules.
  • direct: lib.sh:76-89 modal scan pinned to a Claude Code version.
  • external: the ntfy Stop-hook pattern, Remote Control, and native notify_when_idle.
Rationale
Parallel agents only pay off if you can walk away. Today a blocked agent waits silently. The rules already exist; only the delivery is missing, and that piece is identical on both OSes.
Downsides
It needs a phone channel you trust, such as a self-hosted or private ntfy topic. Some work agents may need a dedicated topic. If it's tuned badly it becomes noise.

6. Append-only task log, derived status, expiring backlog

Idea 6Axis 4 · Durable task recordConfidence 60%Complexity High
Description
Treat a task file like a lab notebook:
  • Append-only. It holds dated, typed entries (decision:, handoff:, done:, follow-up:). Status, "stale" and "needs review" are computed from the latest entries and their age, never stored, and frontmatter shrinks to identity.
  • Planned work expires. Anything untouched for N weeks compacts to one "someday" line and is archived. It comes back only when recalled by #slug.
That keeps the live set small enough that the unused store-wide board and the review ritual have nothing left to do.
Basis
  • direct: limitations.md:51-61 says the schema migration never ran and status values drift.
  • direct: Go plan :37 "Three separate awk-based frontmatter writers"; 183 planned against 22 doing.
  • direct: weekly review is manual-only and has run once.
  • external: beads compaction; the lab-notebook pattern.
Rationale
Every drift bug comes from mutable state kept in sync by several writers. Appends need no lock and merge cleanly across machines. The Go store then needs an append primitive and one fold instead of a frontmatter writer, which shrinks the port before it starts.
Downsides
It changes about 360 existing files and every skill that reads sections. It overlaps the already-planned Go store, so it is best judged as an input to that plan rather than a separate build. Expiry may bury something you wanted.

7. A foreman agent: you manage one, it manages the rest

Idea 7Axis 3 · CoordinationConfidence 45%Complexity Medium
Description
Flip "many sessions you route between" to one long-lived foreman session per day. You talk only to the foreman. It starts background workers (--bg or worktree agents) per task, receives their replies through native messaging and notify_when_idle, and brings up only decisions and permission prompts, which it must pass to you and never answer itself. tmux becomes a place to look, not the control surface. It is the most different direction here, and a direct test of whether one tmux session per task is still the right unit.
Basis
  • external: background sessions, agent view and messaging exist natively; messages from another Claude can't grant consent.
  • direct: the routing machinery (send-keys, boot regex, the '2' keystroke, handoff.sh:219 and :410-412) exists because you are the router; roadmap-handoff.md:133-137 shows a send-keys side effect changing your default model.
Rationale
If it works, most of the coordination layer becomes delegation instead of plumbing. If it doesn't, you learn quickly why the current shape is right.
Downsides
Background sessions are a research preview. The foreman's own context fills up over a day. Inbound message hold rules can stall it. It competes with idea 2 for the same problem, so try it as a spike rather than a plan.

How the set fits together. Idea 1 is the measurement that tells you how much of the rest you need. Ideas 2, 3 and 5 are a thin layer that works on both OSes, built on native features. Idea 4 is the decision the repo merge forces. Idea 6 feeds into the already-planned Go store. Idea 7 is the outlier that challenges the whole shape.
