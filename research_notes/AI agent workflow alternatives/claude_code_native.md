# Claude Code native features for running, tracking and coordinating many parallel sessions (as of 25 Oct 2026)

Scope: what the Claude Code CLI itself provides, for a solo developer on macOS and Ubuntu. Latest version seen in the GitHub CHANGELOG is **v2.1.310** (no date shown) — [CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md). Unless marked "secondary", every source is official Anthropic documentation at code.claude.com/docs or the anthropics/claude-code CHANGELOG. Docs pages were read on 2026-10-25.

## 1. Cross-session messaging (ListAgents / SendMessage, /list-agents, inbox socket)

### Takeaway
Cross-session messaging is GA. It has no experimental label and is on by default from v2.1.224 on macOS and Linux (including WSL 2), and from v2.1.234 on native Windows. Claude in one session can find and message your other local sessions over a per-session Unix socket, with no traffic to Anthropic. A hook or script can post into its own session's socket. Messages never count as your consent, and permission prompts still fire on the receiving side. To reach sessions on other machines, both ends need Remote Control and a claude.ai login.

### Cited Findings
- **Availability/version**: needs v2.1.224+ on macOS, Linux and WSL 2, and v2.1.234+ on native Windows. "When a session meets the requirements, messaging is on with nothing to enable." On Bedrock, Vertex and Foundry, or with feature-flag fetching off, same-machine messaging needs v2.1.248+ — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- Launched in Week 32 (Aug 3–7, 2026), releases v2.1.220 to v2.1.224. The release note says "Available on macOS and Linux. Requires v2.1.224 or later." — [What's new 2026-w32](https://code.claude.com/docs/en/whats-new/2026-w32.md)
- **Tools**: Claude finds targets with `ListAgents` and sends with `SendMessage`. Claude can send on its own initiative, or you can prompt it to. You can name the target with an `@session-name` mention typeahead (v2.1.232+). Names containing spaces need quotes: `@"release notes"` — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Slash command**: `/list-agents`, alias `/peers`. It lists subagents, agent-team teammates, your other local sessions (including background sessions; a session shows up only if it binds an inbox socket), and, while connected to Remote Control, your cloud sessions and Remote Control sessions on other machines (marked `offline` when disconnected). If `/list-agents` is not recognised, the session does not have the feature — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Addressing**: a session answers to the name set by `/rename` or `--name`. Otherwise Claude Code gives it a default name (e.g. `my-app-3f`). If several sessions share a name, Claude adds a short identifier to the address — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md); [Sessions](https://code.claude.com/docs/en/sessions.md)
- **Delivery semantics**: "The receiving Claude reads the message between tool calls during an active turn, so a running tool is never interrupted. When the receiving session is idle, Claude Code starts a new turn with the message." A message is plain text only, never conversation history or files. An `@file` mention inside a message is not attached. A delivered message counts toward usage like a typed prompt — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Display**: the receiver shows a dim preview line, e.g. `› Message from @api-worker: Schema migration finished (ctrl+o to expand)`. `Ctrl+O` opens the full text, and `--verbose` shows the full text inline — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Inbound controls**: the `crossSessionInbound` setting takes `accept`, `hold` (show a notice, don't deliver; held messages are released if `accept` later applies) or `refuse` (drop). It can also be set in `/config` under "Messages from your other sessions" (v2.1.232+). The `/config crossSessionInbound=value` shorthand is rejected. A `refuse` in project or local settings overrides every other source — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Default when no value is set (permission-mode classes)**: if the receiver prompts for permissions, messages are delivered, except that messages from a sender in bypass mode are held. If the receiver bypasses permissions, messages are held unless the sender also bypasses. A held message opens an Approve/Deny dialog that expires after `dialogExpiry` (default 5 minutes). In background sessions with no terminal attached, the dialog stays open past the deadline. At most 100 messages are held, after which the oldest is dropped — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- A background session holding a message for approval shows `approve message from` on its `Needs input` row in agent view (v2.1.257) — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- **`-p` workers**: `claude -p` sessions bind an inbox socket and appear in the listing. Bare mode does not bind one. To accept unattended, start with `crossSessionInbound: "accept"` in `--settings`. `dialogExpiry: "never"` keeps default-held messages until the session ends — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **notify_when_idle**: the `SendMessage` tool's `notify_when_idle` input subscribes to a single notice for when another local session next goes idle (turn finished, nothing queued) or exits. It needs v2.1.236+ in both sessions. Subscribing on its own does not start a turn in the watched session or spend tokens there. The notice can include the turn-finish time and a one-line status. A subscription is dropped after 12 hours with no notice. Only the main conversation's Claude can subscribe, and only to sessions on the same machine (not to teammates, subagents or remote sessions) — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Consent rules**: an incoming message "can't approve anything … never counts as your consent". The receiving Claude is told never to change permission settings, `CLAUDE.md` or other configuration because another session asked. Slash commands in the message text (e.g. `/compact`) arrive as plain text and are not run. Permission prompts still fire. Senders are told not to ask other sessions to do something their own session denied — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Inbox socket**: a Unix domain socket on macOS and Linux, a named pipe on Windows. Its path appears in the `/status` "Peer address" row (prefixed `uds:`). It is exported to hooks and Bash as `CLAUDE_CODE_MESSAGING_SOCKET`, before any hook runs, including `SessionStart`. A per-session token is exported as `CLAUDE_CODE_MESSAGING_TOKEN`. The auth line `{"type":"auth","token":"<token>"}` is optional on macOS and Linux and required on Windows. A connection that has not sent a complete line within 30 s is closed. Access is restricted to your OS user. If the directory is unsafe, Claude Code falls back to `/tmp/cc-socks-<uid>` — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Hooks/scripts posting into a session**: the docs cover this explicitly ("when you want a script or hook to post into a session"). With no `crossSessionInbound` set, a message verified as coming from the session's own child processes (a hook or Bash command posting to its own session's socket) is delivered. Platform difference: on Linux and WSL, Claude Code can verify the sender by process evidence even after the child has exited. On macOS it can only do so while the posting process is still running. Otherwise it relies on the auth line carrying `CLAUDE_CODE_MESSAGING_TOKEN`. If neither check succeeds, a session in bypass mode holds the message for approval. In sandboxed sessions, the socket must be allowed via `sandbox.network.allowAllUnixSockets` or `sandbox.network.allowUnixSockets` — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Cross-machine reach**: same-machine messages go over the socket, never through Anthropic. Messages to another of your machines go through Anthropic servers via that machine's Remote Control connection (v2.1.225+). Messages to cloud sessions go through Anthropic. The sender must be connected to Remote Control (claude.ai login; no API key, Bedrock, Vertex or Foundry) or the message is one-way with no reply address. Cloud sessions cannot reply with `SendMessage`. `isolatePeerMachines: true` requires approval before any message leaves the machine, even in bypass mode. Container and host sessions cannot reach each other, and neither can WSL and native Windows sessions — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Turning it off**: `crossSessionInbound: "refuse"` stops receiving. Permission deny rules `["SendMessage","ListAgents"]` stop sending and listing; denying `SendMessage` also removes messaging to subagents and teammates — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- **Limits**: plain text only; about 1M characters per same-machine message; rapid bursts to one session are refused at the sender; per-sender rate limiting and dedup of identical repeats; at most 50 accepted messages queued, so message loops stop on their own — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- Changelog fixes: v2.1.299 "Fixed `SendMessage` not finding a subagent by name after the CLI restarted and resumed the session"; v2.1.309 "Fixed sessions renamed with `/rename` appearing to other sessions under a generated name" — [CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)

### Inferences
- This could replace a tmux `send-keys` handoff: a session (or a hook in it) can hand findings to a named peer, and delivery waits for a tool-call boundary instead of typing into a live prompt. `notify_when_idle` covers the "tell me when X finishes" case without polling.
- The "own-child" rule means a hook can reliably post only into **its own** session. Posting from an outside script (e.g. a tmux keybinding) into a different session goes through normal inbound rules, so it is delivered by default only when the receiver is not in bypass mode, or when the receiver sets `crossSessionInbound: accept`.
- Ubuntu handles own-child verification better than macOS, because exited children can still be verified on Linux.

### Gaps
- The wire format of a message line on the socket (the JSON schema after the auth line) was not in the sections read. The docs point to it but I did not find the exact schema, so posting from external scripts needs that schema confirmed first.
- No sign of a stable CLI subcommand such as `claude send <session>`. Messaging appears to happen only through Claude's tools or the raw socket.

## 2. Agent view and background sessions (`claude agents`, `--bg`, `/bg`, `/fork`, attach/logs/stop)

### Takeaway
Agent view is a **research preview**, introduced in v2.1.139 (Week 20, May 11–15, 2026) and changed heavily since. A per-user supervisor daemon runs full background Claude sessions without a terminal. `claude agents` is the dashboard, with states Working / Needs input / Idle / Completed / Failed / Stopped. Sessions survive closing the terminal and machine sleep, but **not a reboot or shutdown**: after a restart, sessions active in the last 48 hours show as failed and restart from their saved conversation when you reply. Dispatched sessions move into their own git worktree automatically.

### Cited Findings
- Maturity: "Agent view is in research preview… The interface and keyboard shortcuts may change." Version history: "v2.1.139 Agent view introduced as a research preview" — [Agent view](https://code.claude.com/docs/en/agent-view.md); [What's new 2026-w20](https://code.claude.com/docs/en/whats-new/2026-w20.md)
- **Commands**: `claude agents` (with `--cwd <path>`, `--json`, `--all`); `claude --bg "<prompt>"` / `--background`; `claude --bg --name "<name>" "<prompt>"`; `claude --bg --exec 'pytest -x'` (a shell job that does not invoke the model); `claude --agent <name> --bg`; `claude --resume <id> --bg`; `claude attach <id|name>`; `claude logs <id|name>` (partial names allowed from v2.1.290); `claude stop <id>` (alias `claude kill`); `claude respawn <id>` / `--all`; `claude rm <id>`; `claude daemon status|logs|stop --any`. `--bg` cannot be combined with `-p` — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- `claude agents` also accepts dispatch defaults: `--permission-mode`, `--model`, `--effort`, `--dangerously-skip-permissions`, `--settings`, `--add-dir`, `--plugin-dir`, `--mcp-config` (v2.1.142), `--agent` (v2.1.157) — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- **In-session**: `/bg` or `/background` (optionally `/bg <prompt>`) sends the current conversation to the background. `/fork` copies the conversation into a new background session while the original keeps running (since v2.1.212; the old forked-subagent behaviour moved to `/subtask`). Pressing `←` on an empty prompt backgrounds the session and opens agent view. Since v2.1.221 a `/fork` copy is told to create its own worktree before changing code — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- **States**: Working (animated), Needs input (yellow: a question, permission, sandbox or MCP request), Idle (dimmed), Completed (green), Failed (red), Stopped (grey). Groups: Pinned, Ready for review, Needs input, Working, Completed. Rows carry PR badges coloured by check status. `✢` marks a `/loop` session sleeping between iterations — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- **Keys**: `Enter`/`→` attach; `Space` opens a peek panel (reply without attaching); `Alt+1..9` attach; `Ctrl+S` group by state or directory; `Ctrl+T` pin (keeps the process alive); `Ctrl+F` find; `Ctrl+R` rename; `Ctrl+X` twice to stop then delete. While attached, `←` on an empty prompt, `Ctrl+Z` or `/exit` detaches — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- **Persistence**: the supervisor starts automatically and sessions keep running after you close the terminal. Sessions that are idle or waiting and have been unattached for about an hour are stopped to free resources and resume when you attach or reply (pinning prevents this). "Sleep does not stop sessions. They resume on wake. Shutdown or restart does stop running sessions. Those that last made progress within 48 hours show as failed and restart when you reply. Older sessions show as stopped." If the supervisor dies on macOS or Linux, sessions stop unless a new supervisor connects within about a minute. After an auto-update, the supervisor restarts on the new version and migrates idle sessions — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- Limitation: "Sessions are local: background sessions run on your machine. They are preserved across sleep but stop if the machine shuts down." Rate limits scale with the number of parallel sessions — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- Conflict: a secondary blog says background sessions "stop on sleep or shutdown" — [dsebastien.net (secondary)](https://www.dsebastien.net/claude-code-agent-view-one-screen-for-every-background-session/). The official doc says sleep does **not** stop them. Trust the official doc.
- **State files**: `~/.claude/daemon.log`, `~/.claude/daemon/roster.json`, `~/.claude/jobs/<id>/state.json`, and `~/.claude/jobs/<id>/tmp/` (exposed as `$CLAUDE_JOB_DIR`). The jobs files are "not a stable interface"; use `claude agents --json --all` from scripts. `CLAUDE_CONFIG_DIR` gives a separate supervisor instance — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- **Worktrees**: once a dispatched session starts editing, it moves into its own git worktree under `.claude/worktrees/`. This is skipped for sessions backgrounded from an existing terminal, sessions already in a linked worktree, and non-git directories without a `WorktreeCreate` hook. Disable per repo with `{"worktree":{"bgIsolation":"none"}}` (setting added in v2.1.143). Deleting a session removes its worktree only when safe: it refuses if there are unpushed commits or the worktree is in use, and `claude rm` keeps worktrees with uncommitted changes — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- Since v2.1.198, a background session that isolated its work in a worktree commits and pushes its own branch (never main/master) when it finishes. Since Week 32 it opens a draft PR "only when the task calls for one" and follows the git instructions in CLAUDE.md — [Agent view](https://code.claude.com/docs/en/agent-view.md); [What's new 2026-w32](https://code.claude.com/docs/en/whats-new/2026-w32.md)
- **Notifications**: since v2.1.198, agent view sends a notification through `preferredNotifChannel` when a background session needs input, finishes or fails, and fires the `Notification` hook with type `agent_needs_input` or `agent_completed`. Since v2.1.205, the prompt footer in a normal session shows `← 2 agents` (the number of background agents waiting on you) — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- `/status` shows a `Session kind` row (`background job · attached`, `background job · unattended`, or `interactive`), since v2.1.221 — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- **tmux interaction**: background sessions don't report status to the terminal via OSC 7501, even when attached; agent view shows their status instead. Since v2.1.217, the PR badge renders as a hyperlink over SSH and tmux. The docs describe no tmux integration beyond this — [Terminal config](https://code.claude.com/docs/en/terminal-config.md); [Agent view](https://code.claude.com/docs/en/agent-view.md)
- **macOS-specific**: the background host needs separate Files and Folders permission for ~/Desktop, ~/Documents and ~/Downloads, and macOS 15+ Local Network permission. With Homebrew or npm installs, these grants may need repeating after updates; the native installer keeps them — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- **Linux-specific**: since v2.1.247, on Linux and WSL a session whose terminal host process died fails within seconds with a reason — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- Disable: `disableAgentView: true` or `CLAUDE_CODE_DISABLE_AGENT_VIEW`. Open by default: `defaultToAgentsView=true` — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- `claude --resume <session>` on a running background session attaches to it, and a prompt passed on the command line is sent as its next turn (v2.1.285+) — [Sessions](https://code.claude.com/docs/en/sessions.md)
- Community tool (secondary): tmux-claude-session-manager lists sessions and their status by reading `claude agents --json` — [search result (secondary)](https://awesome.ecosyste.ms/projects/github.com%2Fcraftzdog%2Ftmux-claude-session-manager)

### Inferences
- Agent view covers most of a "tmux session + worktree per task + status in tmux" workbench: dispatch, worktree isolation, a state dashboard, attach and detach, and notifications. `claude agents --json` is the supported way to feed a tmux status line if you still want one.
- Two gaps remain against a tmux setup: reboots stop sessions (conversations resume, but running work does not continue), and sessions are not visible tmux panes.

### Gaps
- The exact field names in the `claude agents --json` schema (the docs say a schema exists; it was in a part of the page I did not extract).
- No documented maximum number of concurrent background sessions.

## 3. Agent teams (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`)

### Takeaway
Experimental and off by default. A lead session spawns teammates, which are separate Claude instances with a shared, file-locked task list and per-agent JSON mailboxes. Teammates run in-process by default, or in tmux or iTerm2 split panes. The model is lead-centred: one team per session, no nesting, a fixed lead, and in-process teammates are not restored on resume.

### Cited Findings
- Enable with `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in the environment or in settings.json `env`. Requires an interactive session; under `-p` or the SDK, named subagents run as ordinary subagents. While enabled, any subagent Claude names launches as a teammate, so teams can form without you asking — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Display: the `teammateMode` setting takes `"in-process"` (default), `"auto"` (split panes if already inside tmux or in iTerm2 with `it2`), `"tmux"` or `"iterm2"`. The flag `--teammate-mode` is experimental and hidden from `--help`. Split panes are not supported in the VS Code terminal, Windows Terminal or Ghostty. The docs say "tmux… traditionally works best on macOS" — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Task list states: pending, in progress, completed, with dependencies; claiming uses file locking. Mailbox: `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`. Team config `~/.claude/teams/{team-name}/config.json` is removed at session end. The task list `~/.claude/tasks/{team-name}/` persists and is pruned by `cleanupPeriodDays`. Team name = `session-` plus the first 8 characters of the session ID — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Hooks: `TeammateIdle` (exit 2 keeps the teammate working), `TaskCreated` (exit 2 blocks creation), `TaskCompleted` (exit 2 blocks completion). TeammateIdle input carries `teammate_name` and `team_name`. TaskCreated and TaskCompleted carry `task_id`, `task_subject`, optional `task_description`, `teammate_name`, `team_name` (deprecated), and `agent_id` (v2.1.290+) — [Agent teams](https://code.claude.com/docs/en/agent-teams.md); [Hooks](https://code.claude.com/docs/en/hooks.md)
- Permissions: teammates inherit the lead's mode (except `dontAsk`), and teammate prompts surface in the lead. Split-pane teammates inherit `--disallowedTools` and `--tools` only from v2.1.309, and never `--allowedTools` — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Limitations (verbatim headings): "No session resumption with in-process teammates", "Task status can lag", "Shutdown can be slow", "One team per session", "No nested teams", "No background subagents from in-process teammates", "Lead is fixed: the main session is the lead for its lifetime", "Permissions set at spawn", "Split panes require tmux or iTerm2" — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Recent fixes: v2.1.304 "approving a shutdown request from the main session no longer exits the whole CLI"; v2.1.309 split-pane teammates now inherit deny and `--tools` rules — [CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)
- Orphaned tmux sessions can remain after the lead ends; clean them up with `tmux kill-session` — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)

### Inferences
- Teams suit short, parallel fan-outs inside one lead session. They are not a replacement for long-lived independent per-task sessions (agent view plus cross-session messaging fit that better), because the team dies with the lead and does not resume.

### Gaps
- No version number given for when agent teams first shipped (the feature predates this window; treat it as older than 6 months and still experimental).

## 4. Remote Control (phone/browser)

### Takeaway
Remote Control lets you drive a **local** session from claude.ai/code or the Claude iOS/Android app. Code still runs on your machine. It needs a claude.ai subscription (Pro, Max, Team or Enterprise; no API keys). It sends mobile push notifications. Server mode (`claude remote-control`) runs many sessions from one process and can give each its own worktree.

### Cited Findings
- From the phone or browser you can use your full local environment (filesystem, MCP, tools, `@` file autocomplete), work from several devices at once, send images and files, and change the model and effort (v2.1.238+) — [Remote Control](https://code.claude.com/docs/en/remote-control.md)
- Requirements: "available on Pro, Max, Team, and Enterprise plans. API keys are not supported." Team and Enterprise need an Owner to enable it. It does not work on Bedrock, Vertex or Foundry, or through LLM gateways. Since Week 20 it is disabled when `ANTHROPIC_API_KEY`, `apiKeyHelper` or `ANTHROPIC_AUTH_TOKEN` is set, even alongside a claude.ai login — [Remote Control](https://code.claude.com/docs/en/remote-control.md); [What's new 2026-w20](https://code.claude.com/docs/en/whats-new/2026-w20.md)
- Start: `claude remote-control` (server mode), `claude --remote-control ["Name"]` / `--rc`, or `/remote-control` / `/rc` inside a session. Server flags: `--spawn same-dir|worktree` (press `w` to toggle; the choice is saved per folder), `--capacity <N>` (default 32), `--[no-]create-session-in-dir`, `-c/--continue`, `--session-id <id>` (v2.1.200+), `--remote-control-session-name-prefix` — [Remote Control](https://code.claude.com/docs/en/remote-control.md)
- Auto-connect: the `/config` option "Enable Remote Control for all sessions" (setting `remoteControlAtStartup`). Since Week 32, project and local settings can only turn it off — [Remote Control](https://code.claude.com/docs/en/remote-control.md); [What's new 2026-w32](https://code.claude.com/docs/en/whats-new/2026-w32.md)
- **Push notifications**: "Claude decides when to push. It typically sends one when a long-running task finishes or when it needs a decision." `/config` toggles: "Push when Claude decides" and "Push when actions required". There is no per-event configuration. Pushes are skipped while you are focused on the terminal; set `CLAUDE_CLIENT_PRESENCE_FILE` to a marker file to suppress them while you are at the machine — [Remote Control](https://code.claude.com/docs/en/remote-control.md)
- Limits: one remote session per interactive process (use server mode for more). The local process must keep running ("start it inside `tmux`" on remote machines). Server-mode sessions can be brought back for about 4 hours after the server stops. An interactive session disconnects after about 30 minutes without heartbeats. Forwarded dialogs other than permission prompts expire after `dialogExpiry` (5 minutes) — [Remote Control](https://code.claude.com/docs/en/remote-control.md)
- Optional security: "Trusted Devices" requires a sign-in less than 18 hours old plus a biometric or passkey step-up — [Remote Control](https://code.claude.com/docs/en/remote-control.md)

### Inferences
- Remote Control is also the prerequisite for messaging across machines (macOS laptop to Ubuntu work machine): both sessions must be connected and signed in to claude.ai. If the Ubuntu work machine uses an API key or gateway, cross-machine reach is unavailable there.

### Gaps
- No version or date found for when Remote Control first shipped (likely more than 6 months old; unconfirmed). Push notifications are referenced in [What's new 2026-w16](https://code.claude.com/docs/en/whats-new/2026-w16.md) (April 2026; not opened in detail).

## 5. Hooks for status and checkpointing

### Takeaway
There are now 33 hook events, including `Notification` with `agent_needs_input` and `agent_completed` types for background sessions. Hook types are command, http, mcp_tool, prompt and agent (agent is experimental). Plugins can ship hooks. `SessionStart` and `UserPromptSubmit` carry a `session_title` field when the session has a custom name. The docs do **not** show a session name in the `Notification` payload, but a hook can map `session_id`/`cwd` to a session, or read `CLAUDE_CODE_MESSAGING_SOCKET`.

### Cited Findings
- **Event list**: `SessionStart`, `Setup`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Notification`, `MessageDisplay`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`, `Elicitation`, `ElicitationResult`, `SessionEnd` — [Hooks](https://code.claude.com/docs/en/hooks.md)
- **Common input fields**: `session_id`, `prompt_id`, `transcript_path` (written asynchronously, may lag), `cwd` (follows worktree moves; `CLAUDE_PROJECT_DIR` does not), `scratchpad_dir` (v2.1.257+), `permission_mode`, `effort.level`, `hook_event_name`, and `agent_id`/`agent_type` inside subagents — [Hooks](https://code.claude.com/docs/en/hooks.md); [Worktrees](https://code.claude.com/docs/en/worktrees.md)
- **Notification**: input fields are `message`, optional `title`, and `notification_type`. Types: `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`, `elicitation_url_dialog`, `elicitation_complete`, `elicitation_response`, `agent_needs_input`, `agent_completed`, `quota_auto_resume_fired`, `quota_auto_resume_stale`, `quota_auto_resume_disabled`, `plugin_notification`. Notification hooks cannot block or change notifications — [Hooks](https://code.claude.com/docs/en/hooks.md)
- **SessionStart**: `source` is `startup|resume|clear|compact|fork`; optional `model`, `agent_type`, and `session_title` (custom names only, set by `--name`, `/rename` or a hook's `sessionTitle` output; generated titles are not included). On resume or fork (v2.1.251+) it also carries `seconds_since_last_response`, `context_tokens`, `prompt_cache_likely_expired` and `estimated_cache_write_usd`. Outputs: `additionalContext`, `initialUserMessage`, `sessionTitle` (a hook can name the session), `watchPaths`, `reloadSkills`. `CLAUDE_ENV_FILE` persists env vars. Only `command` and `mcp_tool` hook types are supported — [Hooks](https://code.claude.com/docs/en/hooks.md)
- **UserPromptSubmit**: `prompt`, plus `session_title` when the session has a custom title; can block — [Hooks](https://code.claude.com/docs/en/hooks.md)
- **Stop**: `stop_hook_active`, `last_assistant_message`, `background_tasks`, `session_crons`; can block (`decision: "block"` + `reason`, or `additionalContext`) with an 8-continuation loop guard. **SubagentStop** adds `agent_id`, `agent_type`, `agent_transcript_path`. **StopFailure** fires on API errors and its output is ignored except `terminalSequence` — [Hooks](https://code.claude.com/docs/en/hooks.md)
- **SessionEnd**: `reason` is `clear|resume|logout|prompt_input_exit|other`; no decision control. v2.1.300 fixed SessionEnd sometimes not running when exiting with a background command still running — [Hooks](https://code.claude.com/docs/en/hooks.md); [CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)
- **PreCompact**: `trigger` (`manual|auto`), `custom_instructions`. **PostCompact**: `trigger`, `compact_summary` — [Hooks](https://code.claude.com/docs/en/hooks.md)
- **Hook types**: `command` (shell form, or exec form with `args`, added Week 20), `http` (POSTs the input JSON to a URL and reads a JSON response), `mcp_tool`, `prompt`, `agent` (experimental). Async options: `"async": true`; `"asyncRewake": true` wakes Claude on exit 2 even when the session is idle — [Hooks](https://code.claude.com/docs/en/hooks.md); [What's new 2026-w20](https://code.claude.com/docs/en/whats-new/2026-w20.md)
- `terminalSequence` output field (Week 20): "lets hooks emit desktop notifications, window titles, and bells without a controlling terminal" — [What's new 2026-w20](https://code.claude.com/docs/en/whats-new/2026-w20.md)
- **Plugin hooks**: `hooks/hooks.json` in a plugin, merged with user and project hooks; use `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}` — [Hooks](https://code.claude.com/docs/en/hooks.md)
- **Env vars for hooks**: `CLAUDE_PROJECT_DIR`, `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA`, `CLAUDE_EFFORT`, `CLAUDE_CODE_REMOTE`, `CLAUDE_CODE_BRIDGE_SESSION_ID` (Remote Control, v2.1.199+), `CLAUDE_CODE_MESSAGING_SOCKET`/`_TOKEN` — [Hooks](https://code.claude.com/docs/en/hooks.md); [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- v2.1.302: "at most 12 of one event run at a time" for prompt and agent hooks — [CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)

### Inferences
- For a tmux status integration: `UserPromptSubmit` (working), `Stop` (idle), `Notification` with `permission_prompt`/`idle_prompt` (needs input), and `SessionEnd` give the same signals a hand-built hook system uses. For sessions run under agent view, `claude agents --json` makes most of that hook work unnecessary.

### Gaps
- Whether `session_title` is also present in Notification and Stop payloads is unconfirmed; the excerpts I read list it only for SessionStart and UserPromptSubmit.
- The full `http` hook config keys (headers, env-var interpolation allowlist) were not extracted.

## 6. Session naming/resume, worktrees, task lists, memory/checkpoints

### Takeaway
There is built-in `--worktree`/`-w` support, including `#PR` worktrees, `.worktreeinclude`, enforced isolation, cleanup prompts and automatic sweeps. There are named sessions (`-n`/`--name`, `/rename`), resume by name or ID, `/branch` and `--fork-session`. The to-do task list can be shared across sessions with `CLAUDE_CODE_TASK_LIST_ID`. Checkpoints with `/rewind` track only Claude's file-tool edits. These are mature, documented features rather than previews, though the docs do not label them GA.

### Cited Findings
- **Worktrees**: `claude --worktree <name>` (or `-w`) creates `.claude/worktrees/<name>/` on branch `worktree-<name>`; omit the name for a generated one. `claude --worktree "#1234"` or a PR/MR URL fetches the PR head (GitLab support v2.1.233+). `worktree.baseRef`: `"fresh"` (default, the remote default branch) or `"head"`. `.worktreeinclude` copies gitignored files such as `.env`. Reusing a name reopens the worktree. `EnterWorktree`/`ExitWorktree` tools; `isolation: worktree` in subagent frontmatter; `WorktreeCreate`/`WorktreeRemove` hooks for custom or non-git setups — [Worktrees](https://code.claude.com/docs/en/worktrees.md)
- Cleanup: a clean, unnamed worktree is auto-removed on exit; named or dirty ones prompt. `-p` runs never clean up. A periodic sweep removes subagent and background-session worktrees older than `cleanupPeriodDays` unless they hold work. Running agents hold a `git worktree lock` — [Worktrees](https://code.claude.com/docs/en/worktrees.md)
- Isolation enforcement blocks edits, command working directories, git redirects (`git -C`, `GIT_DIR`) and unverifiable command shapes that reach the main checkout. It does not catch `cp` or shell redirects. The isolation check was extended in Week 32 — [Worktrees](https://code.claude.com/docs/en/worktrees.md); [What's new 2026-w32](https://code.claude.com/docs/en/whats-new/2026-w32.md)
- Shared across worktrees: `.git`, project-scope plugins (v2.1.200+), "don't ask again" approvals (saved to the main checkout from v2.1.211), and untracked `.claude/skills|agents|commands` (v2.1.277+ for skills) — [Worktrees](https://code.claude.com/docs/en/worktrees.md)
- **Sessions**: `claude -n <name>` / `--name`, `/rename`, `Ctrl+R` in the picker; `claude --continue`; `claude --resume [<name>|<id>|<path>]`; `claude --from-pr <n>`; `/resume`; `/branch [name]`; `--fork-session`. Unnamed sessions get a display name such as `my-app-3f` (not usable for resume) and a Haiku-generated title (usable for resume). Transcripts live at `~/.claude/projects/<project>/<session-id>.jsonl` with 30-day retention (`cleanupPeriodDays`). `claude -p --resume <id> --output-format json "..."` lets a script query a session — [Sessions](https://code.claude.com/docs/en/sessions.md)
- **Task list**: Claude's to-do checklist (Task tools), toggled with `Ctrl+T`, persists across compaction. "To share a task list across sessions, set `CLAUDE_CODE_TASK_LIST_ID` to use a named directory in `~/.claude/tasks/`: `CLAUDE_CODE_TASK_LIST_ID=my-project claude`". The tools are on by default for Opus 4.7, Sonnet 4.6, Haiku 4.5 and earlier; other models need `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`. `/tasks` shows running shells and subagents — [Interactive mode](https://code.claude.com/docs/en/interactive-mode.md)
- **Session recap**: a one-line recap appears when you return after 3+ minutes away (terminal unfocused, at least 3 turns); `/recap` generates one on demand — [Interactive mode](https://code.claude.com/docs/en/interactive-mode.md)
- **Checkpoints**: one per prompt, the 100 most recent kept, saved with the conversation (so they survive resume), pruned after about 30 days. `/rewind` or `Esc Esc` offers restore code and/or conversation, "Summarize from here" and "Summarize up to here". Not tracked: files changed only by Bash, most subagent edits, external edits or other sessions' edits, symlinked or hard-linked files. "Not a replacement for version control" — [Checkpointing](https://code.claude.com/docs/en/checkpointing.md)
- **Memory**: CLAUDE.md/AGENTS.md plus "auto memory" (automatic learnings), stored per project under `~/.claude/projects/<project>/memory/` — [Docs index](https://code.claude.com/docs/llms.txt); [Sessions](https://code.claude.com/docs/en/sessions.md)
- `/goal <condition>` (v2.1.139) keeps Claude working across turns until a fast model judges the condition met. It works in interactive, `-p` and Remote Control sessions — [What's new 2026-w20](https://code.claude.com/docs/en/whats-new/2026-w20.md)

### Inferences
- `CLAUDE_CODE_TASK_LIST_ID` together with agent view and worktrees could replace a per-task markdown task file only for Claude's own checklist. It is not a human-curated backlog, and its on-disk format is internal.
- Symlinked dotfiles (e.g. stow-managed config) are skipped by `/rewind`, which matters for a dotfiles repo.

### Gaps
- I did not read the auto memory details page (memory.md); its exact behaviour and settings are unverified here.

## 7. Native notifications (desktop, bell, mobile push, terminal status)

### Takeaway
Out of the box, Claude Code sends OSC desktop notifications in Ghostty, Kitty and iTerm2 (these also work over SSH). `preferredNotifChannel: "terminal_bell"` covers other terminals. OSC 7501 terminal status works from v2.1.295 but not inside tmux. Mobile push comes through Remote Control. Agent view adds background-session notifications. Inside tmux you need `allow-passthrough on`.

### Cited Findings
- "By default Claude Code sends a desktop notification only in Ghostty, Kitty, and iTerm2." Others: `{"preferredNotifChannel": "terminal_bell"}` or a Notification hook. Ghostty and Kitty forward over SSH; iTerm2 needs "Send escape sequence-generated alerts" enabled — [Terminal config](https://code.claude.com/docs/en/terminal-config.md)
- tmux needs `set -g allow-passthrough on`, `set -g focus-events on`, `set -s extended-keys on`, `set -as terminal-features 'xterm*:extkeys'`, or notifications and the progress bar never reach the outer terminal — [Terminal config](https://code.claude.com/docs/en/terminal-config.md)
- OSC 7501 Program Status Protocol: in supporting terminals, each interactive session's working, waiting or done state is shown by the terminal (v2.1.295+). It does not work inside tmux or for background sessions. `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` disables it. Otherwise Claude Code prefixes the tab title with a status glyph — [Terminal config](https://code.claude.com/docs/en/terminal-config.md)
- Mobile push: requires Remote Control; `/config` "Push when Claude decides" and "Push when actions required" — [Remote Control](https://code.claude.com/docs/en/remote-control.md)
- Background sessions: notifications on needs-input, completed and failed via `preferredNotifChannel`, plus `Notification` hook types `agent_needs_input` and `agent_completed` (v2.1.198) — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- Hooks can emit notifications, titles and bells via the `terminalSequence` output field, even without a controlling terminal — [What's new 2026-w20](https://code.claude.com/docs/en/whats-new/2026-w20.md)
- Channels (research preview): MCP-server plugins (Telegram, Discord, iMessage, fakechat, or custom webhook receivers) push events into a running session via `claude --channels plugin:<name>@<marketplace>`. Requires Bun and claude.ai or Console auth. Custom channels need `--dangerously-load-development-channels`. Permission relay is possible — [Channels](https://code.claude.com/docs/en/channels.md)

### Inferences
- On Ubuntu with gnome-terminal, there are no native desktop notifications by default. Use `terminal_bell`, a Notification hook calling `notify-send`, or a terminal like Ghostty or Kitty.
- Channels with a custom webhook receiver are another supported way for external scripts to inject events into a session, separate from the messaging socket.

### Gaps
- No documented Linux-specific desktop notification support (libnotify) beyond the hook route.
