# Keeping personal and employer content separate across one dotfiles setup and AI-agent tooling (macOS personal + Ubuntu work), 2026

Research date: 25 Oct 2026. Claude Code docs cited are the live code.claude.com pages as fetched on that date (they reference versions up to roughly v2.1.288).

## 1. Dotfiles managers and layering: which handle a personal base plus a work overlay, and how is the overlay kept private?

### Takeaway
chezmoi is the strongest fit for "one repo, two OSes, two identities". Its templates branch on `.chezmoi.os` and on per-machine data (for example `work = true`) kept in a local, uncommitted config file. A private work overlay can be pulled in as a separate repo (`.chezmoiexternal`) so employer config never lands in the personal repo. yadm does the same job with filename suffixes (`##os.Darwin`, `##class.Work`). Nix home-manager supports a "private flake input with a public stub", but it costs the most to adopt. GNU stow has no native conditionals, so the split has to be done by package naming and `*.local` files that stay out of git.

### Cited Findings
- chezmoi per-machine data lives in `~/.config/chezmoi/chezmoi.$FORMAT` (e.g. `[data] email = "me@home.org"`), which templates read as `{{ .email }}`. The docs advise permissions `0600` if it holds private data. — [chezmoi: machine-to-machine differences](https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/)
- chezmoi templates branch on `{{ if eq .chezmoi.os "darwin" }}` and `.chezmoi.hostname`. `.chezmoiignore` is itself a template, so whole files can be skipped per OS, e.g. `{{ if ne .chezmoi.os "darwin" }} Library/Application Support/... {{ end }}`. The docs say `ne` is deliberate because chezmoi installs everything by default. — [chezmoi docs](https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/)
- For completely different per-OS files, chezmoi can `include ".bashrc_darwin"` / `".bashrc_linux"` from one `dot_bashrc.tmpl`, or share content through `.chezmoitemplates/`. — [chezmoi docs](https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/)
- Practitioner advice (Aug 2026): "I prefer semantic local data such as `work = true` over scattering hostnames throughout templates", because roles survive a laptop replacement. Ship a work-only git include conditionally so personal machines never receive it. Use `.chezmoi.toml.tmpl` prompts at `chezmoi init`. "`private_` is not encryption. It controls permissions on the destination." "A private Git repository reduces exposure; it does not turn committed secrets into a good idea." Prefer password-manager templates (Git stores a reference) over encrypted blobs that persist in history. — [Larvitz blog, 12 Aug 2026](https://blog.hofstede.it/chezmoi-and-git-dotfiles-without-pretending-every-machine-is-the-same/)
- Same post: keep chezmoi auto-commit/auto-push off and review diffs, because "a dotfiles repository is executable infrastructure for my user account". Filenames like `token`, `credentials`, `known_hosts` and `trustdb.gpg` are warning signs before a first commit. — [Larvitz blog](https://blog.hofstede.it/chezmoi-and-git-dotfiles-without-pretending-every-machine-is-the-same/)
- Observed overlay pattern: a primary personal chezmoi repo plus a separate private work repo pulled into `~/.config/work` via `.chezmoiexternal.toml.tmpl`, with work mode switched by a data flag at init. — [ThisDevDane/dotfiles (search-result summary only; the page refused connections when fetched)](https://mymirror.duckdns.org/ThisDevDane/dotfiles)
- Other public repos use `personal = true` / `work = true` flags in chezmoi config to vary packages and files. — [mauvehed dotfiles](https://tangled.org/mauvehed.com/dotfiles). Others route git identity with `includeIf "gitdir:..."` and use chezmoi only to make sure the files exist, e.g. work identity applied automatically under `~/work/`. — [matzxrr/dots](https://github.com/matzxrr/dots); [rednafi: Migrating from GNU stow to chezmoi](https://rednafi.com/misc/chezmoi/)
- yadm alternates: append `##` conditions to a filename, e.g. `example.txt##os.Darwin,hostname.host1`. Supported attributes include `os` (uname -s), `class`, `hostname`, `distro`, `distro_family`, `arch`, `user`, `default`, with `~` to negate. Class is set per host with `yadm config local.class Work` (add more with `--add`) and is stored locally, not in the repo. A template beats any symlink alternate, more matching conditions win, and with no valid match and no `##default`, no link is made. Files listed in `$HOME/.config/yadm/encrypt` are encrypted. — [yadm alternates](https://yadm.io/docs/alternates)
- Nix: conao3's config expects a sibling checkout of a private `nix-flakes` repo, and a public stub repo satisfies the same interface so the public flake still evaluates. — [conao3/nixos-configuration README](https://cdn.jsdelivr.net/gh/conao3/nixos-configuration@master/README.md). Cu3PO42's gleaming-glacier is built to be consumed from another flake, which the author does "for the configurations of my machines at work". — [gleaming-glacier](https://github.com/Cu3PO42/gleaming-glacier/blob/master/README.md). Home Manager runs standalone on macOS or Linux (`home-manager switch --flake .`). Public repos pair it with agenix or sops-nix for secrets. — [zazedd/.dotfiles](https://github.com/zazedd/.dotfiles); [delafthi/dotfiles](https://zff.dev/delafthi/dotfiles)

### Inferences
- For Jet's current setup (a stow-style repo with per-tool packages such as `nvim/`, `tmux/`, `scripts/`), the cheapest change is probably: (a) keep the stow repo as the personal, public-safe base; (b) put every work-only file in a separate private repo (on the employer's Git host or a private personal repo, depending on policy) cloned only on the Ubuntu box and stowed as its own package, or sourced from `*.local` hooks (`~/.zshrc.local`, `~/.gitconfig.local`, `~/.config/tmux/local.conf`) that the base repo includes but never tracks. Moving to chezmoi pays off if per-OS conditionals keep growing.
- With any tool, the privacy guarantee comes from employer content living in a different repo, ideally hosted under the employer's control. Encryption inside the personal repo is a second line of defence, not the main one.
- Recent deletions in the repo's git status (e.g. `scripts/.config/scripts/tmux/ms-clients.sh`) suggest employer-specific scripts have already been in the personal repo. Its history may need auditing (e.g. `git log --all -- <path>`, or gitleaks).

## 2. Git identity routing: includeIf, direnv, separate GitHub accounts/PATs, gh auth switching

### Takeaway
Git's conditional includes cover identity routing natively. `gitdir:` matches the directory a repo lives in. `hasconfig:remote.*.url:` (Git 2.36+) matches the remote URL, so a work-org clone gets the work identity wherever it sits on disk. Pair it with per-identity `core.sshCommand` / SSH host aliases with `IdentitiesOnly yes`. Use `gh auth switch` or `GH_TOKEN`/`GH_CONFIG_DIR` (for example via direnv) to choose the GitHub account.

### Cited Findings
- `includeIf.<condition>.path` is ignored when the condition is false. `gitdir:` arrived with the feature in Git v2.13.0. `~/` expands to `$HOME`, a trailing `/` means recursive (`foo/` = `foo/**`), and `gitdir/i:` is case-insensitive (useful on macOS's case-insensitive APFS default). For linked worktrees, the match is against the final `.git` directory. — [git-config docs](https://git-scm.com/docs/git-config)
- `hasconfig:remote.*.url:<glob>` matches if any configured remote URL matches. Files included through it may not themselves contain remote URLs (this breaks a cycle). It is meant to sit in global config while the remote URL lives in the repo's local config. `onbranch:` and `worktree:` conditions also exist. — [git-config docs](https://git-scm.com/docs/git-config)
- `hasconfig:remote.*.url` needs Git 2.36+. It is slightly slower than path matching. Example: `hasconfig:remote.*.url:https://github.com/**` → `~/.gitconfig-github`; `https://gitlab.company.com/**` → `~/.gitconfig-work`. The per-identity file can set `core.sshCommand` to force a key with `IdentitiesOnly`. SSH remotes need patterns like `git@github.com:*/**`. Later includes override earlier ones, so specific org patterns go last. — [nite07: Git IncludeIf for multiple identities](https://www.nite07.com/en/posts/git-includeif/); [meziantou](https://www.meziantou.net/using-git-conditional-includes-for-multiple-configurations.htm)
- `gh auth switch [--hostname H] [--user U]` changes the active account for a host. With exactly two accounts on a host it toggles automatically. `gh auth status` lists accounts. — [gh auth switch manual](https://cli.github.com/manual/gh_auth_switch)

### Inferences
- A robust pattern: global `~/.gitconfig` (in the personal repo) holds the personal identity by default, plus `[includeIf "hasconfig:remote.*.url:git@github.com:EMPLOYER-ORG/**"] path = ~/.gitconfig.work` and a `gitdir:~/work/` fallback. `~/.gitconfig.work` is not in the personal repo (on the work box it can come from the private overlay). This works the same on macOS and Ubuntu.
- `hasconfig` routing can also feed AI-agent routing (section 4): one source of truth, "which org owns this remote", decides both commit identity and the realm for agent records.
- direnv (`.envrc` in `~/work/` exporting `GH_TOKEN`, `GH_CONFIG_DIR`, `CLAUDE_CONFIG_DIR`) is a common way to scope env per directory tree. I did not fetch a primary source for it here (see Gaps).

### Gaps
- `core.sshCommand` / `credential.<url>.username` semantics were not read from the primary page (fetch truncated). Descriptions rely on general knowledge and secondary blogs.
- No primary source fetched for direnv or for how `GH_TOKEN`/`GH_CONFIG_DIR` interact with `gh auth switch`.
- Memory note: Jet does gh/git auth with a PAT himself. Per-host credential-helper scoping (`credential.useHttpPath`) for two GitHub accounts on the same host was not verified.

## 3. Claude Code specifics: settings precedence, CLAUDE.md layering, managed settings, where transcripts and memory live, keeping work data out of personal sync, plugin marketplaces per machine

### Takeaway
Everything Claude Code writes during work (full transcripts, auto memory, prompt history, file snapshots, plans, tasks) lives as plaintext under `~/.claude` (or `$CLAUDE_CONFIG_DIR`), keyed by project path. None of it should ever be in a dotfiles repo. Sync only authored config (`CLAUDE.md`, `rules/`, `skills/`, `agents/`, `settings.json`). Ship the work-only parts through a private overlay, through `CLAUDE.local.md` / `settings.local.json`, or through the employer's managed settings. `CLAUDE_CONFIG_DIR` gives a fully separate profile per realm, with known gotchas on macOS.

### Cited Findings
**Settings precedence**
- Scopes: User `~/.claude/settings.json`; Shared project `.claude/settings.json`; Project local `.claude/settings.local.json`; Managed. Precedence, highest first: managed > `--settings` CLI > project local > shared project > user. List keys such as `permissions.allow` merge across files. — [Claude Code settings](https://code.claude.com/docs/en/settings)
- The first time Claude Code writes `.claude/settings.local.json` in a repo, it adds `**/.claude/settings.local.json` to the global git excludes file (`core.excludesFile`, else `~/.config/git/ignore`). — [settings](https://code.claude.com/docs/en/settings)
- `~/.claude.json` (separate from `~/.claude/`) holds account details, MCP server configs, per-project trust state and global config keys. — [settings](https://code.claude.com/docs/en/settings)
- `CLAUDE_CONFIG_DIR` moves settings, session history and plugins to another directory. — [settings](https://code.claude.com/docs/en/settings); [.claude directory](https://code.claude.com/docs/en/claude-directory)
- If `~/.claude/settings.json` isn't writable (e.g. a tool generates it or links it read-only), in-app changes such as `/model` last only for that session. Relevant to stow/home-manager symlinked or read-only settings. — [settings](https://code.claude.com/docs/en/settings)
- `syncClaudeAiSkills` and `syncClaudeAiPlugins` can be set to `false` from user or local settings even when managed settings say `true`. This stops claude.ai account-synced skills and plugins from arriving on a machine. — [settings, exceptions table](https://code.claude.com/docs/en/settings)

**CLAUDE.md layering**
- Managed CLAUDE.md: macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`, Linux `/etc/claude-code/CLAUDE.md`. Then user `~/.claude/CLAUDE.md`, project `CLAUDE.md`, and `./CLAUDE.local.md` (personal, gitignored). All discovered files are concatenated, not overridden. Files are ordered root → cwd, and `CLAUDE.local.md` comes after `CLAUDE.md` at each level. — [Claude Code memory](https://code.claude.com/docs/en/memory)
- `@path` imports (relative or absolute, up to 4 hops). External imports in project files trigger a one-time approval dialog. Imports in user-scope files (`~/.claude/CLAUDE.md`, `~/.claude/rules/`) load without the dialog. A gitignored `CLAUDE.local.md` exists only in one worktree, so the docs suggest importing `@~/.claude/my-project-instructions.md` instead. `claudeMdExcludes` (globs on absolute paths, any settings layer) can skip CLAUDE.md files. The managed CLAUDE.md cannot be excluded. — [memory](https://code.claude.com/docs/en/memory)
- `~/.claude/rules/*.md` apply to every project on the machine and support `paths:` frontmatter. — [memory](https://code.claude.com/docs/en/memory)

**Managed settings**
- File-based managed settings: macOS `/Library/Application Support/ClaudeCode/managed-settings.json`, Linux/WSL `/etc/claude-code/managed-settings.json`, plus an optional `managed-settings.d/*.json` drop-in directory and `managed-mcp.json`. Server-managed settings come from the claude.ai admin console. — [managed settings](https://code.claude.com/docs/en/managed-settings)
- Managed keys relevant to realm separation include `forceLoginOrgUUID` / `forceLoginMethod` (pin login to an org), `strictKnownMarketplaces` / `blockedMarketplaces` (restrict plugin marketplace sources), `permissions.deny`, `sandbox.enabled`, and `cleanupPeriodDays`. A developer with local admin rights can edit the managed source themselves. — [managed settings](https://code.claude.com/docs/en/managed-settings); [memory](https://code.claude.com/docs/en/memory)
- `/status` shows a "Setting sources" line naming the managed source in effect. — [settings](https://code.claude.com/docs/en/settings)

**Where transcripts and memory live**
- Auto memory: `~/.claude/projects/<project>/memory/` (MEMORY.md + topic files). `<project>` comes from the git repository, so all worktrees and subdirectories share one memory dir. Outside git, the project root is used. "Auto memory is machine-local … not shared across machines." `autoMemoryDirectory` can relocate it from any settings scope (user, project, local, policy, `--settings`). `autoMemoryEnabled: false` turns it off per project. — [memory](https://code.claude.com/docs/en/memory)
- Transcripts: `projects/<project>/<session>.jsonl` is the "Full conversation transcript: every message, tool call, and tool result". Also under `~/.claude`: `subagents/`, `tool-results/`, `file-history/`, `plans/`, `paste-cache/`, `tasks/`, `uploads/`. These are deleted after `cleanupPeriodDays` (default 30, minimum 1). `history.jsonl` (typed prompts with project path) is kept until you delete it. Memory files are excluded from the sweep. — [.claude directory](https://code.claude.com/docs/en/claude-directory)
- "These files are plaintext. Anything that passes through a tool is written to a transcript on disk." Mitigations: lower `cleanupPeriodDays`; `CLAUDE_CODE_SKIP_PROMPT_HISTORY` to skip transcripts and history; `--no-session-persistence` with `-p`; deny-read rules for credential files. — [.claude directory](https://code.claude.com/docs/en/claude-directory)
- `claude purge <path>` (`--dry-run`, `--all`, `-i`) deletes one project's transcripts, auto memory, tasks, file-history, its `history.jsonl` lines and its `~/.claude.json` entry. It leaves `backups/` and `shell-snapshots/`. — [.claude directory](https://code.claude.com/docs/en/claude-directory)
- The session scratchpad lives outside `~/.claude`: macOS `/private/tmp/claude-<uid>/<project>/<session>/scratchpad/`, Linux `/tmp/claude-<uid>/...`. — [.claude directory](https://code.claude.com/docs/en/claude-directory)
- Plugins: `~/.claude/plugins` holds cloned marketplaces, installed versions and `installed_plugins.json`. Plugins synced from a claude.ai account land in `~/.claude/plugins/synced/`. — [.claude directory](https://code.claude.com/docs/en/claude-directory)
- Files the docs list as committable/authored (safe to dotfile): `CLAUDE.md`, `rules/`, `settings.json`, `skills/`, `commands/`, `agents/`, `output-styles/`, `workflows/`, `agent-memory/`. Global-only and not for commit: `~/.claude.json`, `projects/<project>/memory/`, `keybindings.json`, `themes/`. — [.claude directory](https://code.claude.com/docs/en/claude-directory)

**Separate profiles per account (practitioner)**
- Common pattern: an alias or env per realm sets `CLAUDE_CONFIG_DIR` (e.g. `~/.claude-personal`), with a separate login per dir. This isolates credentials, settings, history and plugins. Don't copy `~/.claude` wholesale, since that copies credentials and history. — [wmedia: multiple profiles](https://wmedia.es/en/tips/claude-code-multiple-profiles-config-dir); [Codeminer42](https://blog.codeminer42.com/ai-tip-running-two-claude-code-accounts/); [aident.ai](https://aident.ai/blog/use-multiple-claude-code-accounts-safely)
- Directory auto-switch with zsh `add-zsh-hook chpwd`. A function sets `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_OAUTH_TOKEN` based on `$PWD` (e.g. under `~/personal/`). Gotchas: on macOS credentials sit in one Keychain entry (`Claude Code-credentials`) that `CLAUDE_CONFIG_DIR` does not separate, so a second login overwrites the first. The workaround is a per-account `CLAUDE_CODE_OAUTH_TOKEN` (from `setup-token`, paid plans only) kept in Keychain. The account is fixed at process launch. — [deku.posstree.com, 18 Jun 2026](https://deku.posstree.com/en/generative_ai/claude-code-multi-account/)
- With `CLAUDE_CONFIG_DIR` set, `.claude.json` is read from inside the config dir rather than `~/.claude.json`. One author symlinks skills, CLAUDE.md, settings and plugins between profiles and keeps credentials, `projects/` transcripts, folder trust and MCP OAuth tokens separate. The same author's `claude-pickup` script copies a work transcript into the personal tree, a cross-realm leak the post does not discuss. — [DEV: "One brain, two wallets"](https://dev.to/daksh-gargas/one-brain-two-wallets-two-claude-code-accounts-on-one-machine-5ejb)

### Inferences
- On a dedicated work Ubuntu machine, the simplest isolation is physical: the work box's `~/.claude/projects/` only ever holds work transcripts and memory, and the dotfiles repo must never track `~/.claude/projects`, `history.jsonl`, `file-history`, `plans`, `tasks`, `.claude.json` or `.credentials.json`. An allow-list approach (stow only `CLAUDE.md`, `rules/`, `skills/`, `agents/`, `settings.json`) is safer than ignore-listing.
- Per-machine Claude config can follow the same base + overlay shape: personal `~/.claude/CLAUDE.md` holds generic preferences and ends with an `@~/.claude/CLAUDE.work.md` import (or a `rules/work-*.md` file) that exists only on the work box via the private overlay. Imports in user-scope files load without a dialog. A missing import file on the Mac is probably harmless, but that is not verified.
- Plugin marketplaces per machine: put `extraKnownMarketplaces` / `enabledPlugins` for employer marketplaces in a work-only settings source (overlay, managed settings, or the employer repo's `.claude/settings.json`), not in the shared user `settings.json`. Set `syncClaudeAiPlugins: false` / `syncClaudeAiSkills: false` on whichever machine should not receive account-synced items. The current session shows claude.ai-synced skills under `~/.claude/skills/synced/`, so this sync is live on the Mac.
- Watch for skills/plugins that write their own records (e.g. compound-engineering's `docs/brainstorms/`, `docs/ideation/`, `reports/` dirs, untracked in this repo). They write into whatever repo is cwd. On a work repo those artifacts are employer content and should follow the employer repo's rules.

### Gaps
- Did not verify whether a missing `@import` target in `~/.claude/CLAUDE.md` produces a warning.
- Did not verify whether the Keychain single-entry limitation still applies in the latest Claude Code (the post is from June 2026). On Ubuntu, credentials are a file in the config dir, so this does not apply there.
- `extraKnownMarketplaces` scope rules beyond "waits for folder trust in project files" were not read in detail.

## 4. Routing agent task records and memory by repo ownership, per-org stores, and hook/pre-commit guards; employer acceptable-use considerations

### Takeaway
Claude Code has no built-in "realm" concept. The building blocks are: auto memory is already per-git-repo; `autoMemoryDirectory` can point a repo's memory at a per-org store from project or local settings; `SessionStart` hooks can inject realm context; `PreToolUse` hooks can deny Write/Edit to paths outside the current realm's store. The usual practice is to derive the realm from the git remote, the same signal `includeIf hasconfig` uses. On the policy side, source code is the most common data type employees leak into personal AI accounts, so work transcripts and memory belong on the employer-sanctioned account and machine.

### Cited Findings
- Auto memory is per git repo (shared across worktrees), stored in `~/.claude/projects/<project>/memory/`. `autoMemoryDirectory` can override it from user, project, local, policy or `--settings` scope. — [memory](https://code.claude.com/docs/en/memory)
- CLAUDE.md and memory are "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook." — [memory](https://code.claude.com/docs/en/memory)
- PreToolUse hook input includes `session_id`, `transcript_path`, `cwd`, `permission_mode`, `tool_name`, `tool_input` (e.g. `file_path`). Block with exit code 2 (stderr becomes the reason) or exit 0 with `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"..."}}`. Matcher `Write|Edit` is an exact-name list; other characters make it an unanchored regex. — [hooks](https://code.claude.com/docs/en/hooks)
- `SessionStart` hooks (matchers `startup`, `resume`, `clear`, `compact`, `fork`) can return `hookSpecificOutput.additionalContext`, which is inserted as a system reminder. `CLAUDE_PROJECT_DIR` is the session's project root and stays fixed even when Claude enters a worktree. — [hooks](https://code.claude.com/docs/en/hooks)
- Managed settings can pin login to an org (`forceLoginOrgUUID`) and restrict marketplaces (`strictKnownMarketplaces`), and a managed `cleanupPeriodDays` also governs Desktop/Cowork transcript retention. — [managed settings](https://code.claude.com/docs/en/managed-settings); [.claude directory](https://code.claude.com/docs/en/claude-directory)
- Shadow-AI context (vendor sources, mixed quality): a summary of the 2026 Verizon DBIR says shadow-AI use on corporate devices rose from 15% to 45% of the workforce, with about two-thirds via personal accounts. LayerX reads the DBIR as finding source code the most common data type moving into ungoverned tools. Netskope figures reportedly put source code at 42% of genAI policy violations and personal-account use at ~47% of enterprise genAI users. — [LayerX](https://layerxsecurity.com/?p=4965); [QueryPie](https://www.querypie.com/en/blog/shadow-ai-risk-cxo-countermeasures); [dope.security roundup](https://dope.security/post/shadow-ai-statistics); [CSA research note, May 2026](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/05/CSA_research_note_shadow_ai_apps_enterprise_20260530-csa-styled.pdf). Treat the exact numbers cautiously: one roundup (stationx) admits miscited sources, and IBM breach-cost figures differ between secondary sources.
- The Samsung case (2023): engineers pasted source code into ChatGPT and the company banned genAI and sped up an internal tool. Surveys suggest an approved alternative works better than a ban alone. — [QueryPie](https://www.querypie.com/en/blog/shadow-ai-risk-cxo-countermeasures)

### Inferences
- Concrete realm-routing design for Jet (macOS personal / Ubuntu work):
  1. **Realm resolver** (one small script in the dotfiles repo, shared by git, shell and Claude hooks): `git remote get-url origin` → if it matches the employer org/host → `work`, else `personal`. Fallback is the machine role (Ubuntu box = work by default).
  2. **SessionStart hook** in user settings: runs the resolver and injects `additionalContext` such as "Realm: work. Task records go in <work store>. Do not write to Apple Notes or personal repos." It could also refuse or warn when the realm doesn't match the machine (e.g. an employer remote on the personal Mac).
  3. **PreToolUse guard** on `Write|Edit` (and `Bash` for `git push`/`cp` patterns): deny writes whose `file_path` falls in the other realm's store (e.g. on the work machine, deny writes into `~/dotfiles/research_notes`, `~/Desktop/projects/*` personal repos or any synced notes folder). Exit 2 with a reason.
  4. **Per-org memory**: in work repos, set `autoMemoryDirectory` via `.claude/settings.local.json` (never committed) to a work-owned store, or leave the default, which is already per-repo and machine-local.
  5. **Git pre-commit guard** in the personal dotfiles repo (pre-commit framework or `core.hooksPath`): reject staged paths matching `.claude/projects/`, `*.jsonl`, `history.jsonl`, `.claude.json`, and content matching the employer's name, domains or internal hostnames; add gitleaks for secrets.
- The decision that matters most is policy, not tooling: check the employer's AI acceptable-use policy for (a) which Claude account/org may be used on employer code (likely an employer Team/Enterprise org, enforceable through `forceLoginOrgUUID`), (b) whether transcripts and memory may leave the work machine, and (c) whether personal skills/plugins may be installed on the work machine. If the employer deploys managed settings, those override anything in the dotfiles.
- Reusing personal skills on the work box is lower-risk in direction (personal → work), but they must not write their outputs back into the personal repo or personal synced stores.

### Gaps
- Found no official Anthropic guidance specifically on a "work/personal split" for individual developers. Guidance is split across settings, memory, managed-settings and .claude-directory docs.
- Found no primary employer AUP examples (actual company policies) covering AI coding-agent transcripts. Statistics are from vendor blogs, not original DBIR/Netskope reports.
- Did not find an existing open-source hook or tool that routes Claude Code records by git remote. The design above is an inference built from documented primitives.

## 5. Practitioner writeups of a "work/personal split" for AI coding setups

### Takeaway
Writeups from 2026 mostly cover running two Claude Code accounts on one machine via `CLAUDE_CONFIG_DIR` plus directory hooks. They focus on billing and credential separation and largely ignore data-boundary risk: several share CLAUDE.md, skills and settings across realms via symlinks, and one copies transcripts across. Dotfiles writeups on work/personal splits are mature (chezmoi data flags, private overlays, includeIf), but none tied the two together for agent memory.

### Inferences
- Jet's case (separate physical machines, different OSes) is easier than the one-machine-two-accounts case most posts cover. Machine boundary + Ubuntu-only work overlay + allow-list syncing of `~/.claude` authored files covers most risk. Remote-based routing hooks are mainly a guard against mistakes (e.g. cloning a personal repo on the work box and letting work context leak into it, or the reverse).
