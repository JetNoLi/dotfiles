# Native Claude Code absorbs wb's plumbing layer

As of late October 2026, Claude Code covers most of what wb's tmux, worktree and status plumbing does, but it still does not cover wb's durable task store or the personal/employer boundary. Agent view (`claude agents`, `--bg`, `/fork`), automatic per-session git worktrees, cross-session messaging (`SendMessage`, `ListAgents`, `notify_when_idle`, on by default since v2.1.224) and Remote Control push between them handle running many sessions, showing which one needs you, passing work between sessions and fanning out. Third-party orchestrators (workmux, agent-deck, Claude Squad, ccmanager) now mostly repeat those features, and none of them offers a real long-running task record. What is still missing natively is the reason wb's 360-file markdown store exists: a curated, multi-day record of tasks with handoffs and decisions that agents read and write. Claude Code's own task lists are internal JSON, not tied to a repo, and wiped on a 30-day cleanup cycle. Nothing native separates work from personal ("realms") either. You build that boundary from git-remote routing, hooks and the physical split between the Mac and the Ubuntu machine. The recommendation: retire wb's send-keys handoffs and most of its session, worktree and status code. Keep the markdown task store and decision shelf, and move both behind hooks. Add a small realm resolver as the one new custom piece. Run direction 1 (native-only control arm) on the Mac first. Two cautions apply. Agent view is still a research preview, and the Ubuntu work machine's ability to use Remote Control depends on employer policy and auth setup, which this research could not confirm.

## Agent view and messaging now cover running and coordinating sessions

The biggest change since wb was built is that background sessions are now built into Claude Code. **Agent view arrived in v2.1.139 in May 2026 as a research preview.** A per-user supervisor daemon runs full Claude sessions with no terminal attached. `claude agents` is the dashboard, with Working, Needs input, Idle, Completed, Failed and Stopped states, PR badges, a peek panel for replying without attaching, and `--json` output for scripts ([Agent view](https://code.claude.com/docs/en/agent-view.md)). When a dispatched session starts editing, it **moves into its own git worktree under `.claude/worktrees/`**. Since v2.1.198 it also commits and pushes its own branch when it finishes. Deleting a session refuses to remove worktrees that hold unpushed or uncommitted work ([Agent view](https://code.claude.com/docs/en/agent-view.md)). Foreground sessions get the same worktree tooling through `claude --worktree`. That includes `#PR` worktrees, `.worktreeinclude` for gitignored files such as `.env`, isolation checks that block edits reaching the main checkout, and `WorktreeCreate` hooks for custom setup ([Worktrees](https://code.claude.com/docs/en/worktrees.md)). Taken together, this covers the "tmux session plus worktree per task" half of wb.

Coordination moved just as far. **Cross-session messaging is GA and on by default from v2.1.224 on macOS and Linux.** Claude finds peers with `ListAgents` and sends plain text with `SendMessage`. Same-machine traffic goes over a per-session Unix socket and never through Anthropic. Delivery waits for a tool-call boundary, so a running tool is never interrupted, and an idle receiver starts a new turn ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)). That is safer than tmux `send-keys`, which types into whatever the prompt happens to hold. The `notify_when_idle` input lets one session subscribe to a single notice when another goes idle or exits, without spending tokens in the watched session. It needs v2.1.236+ in both sessions and expires after 12 hours. Hooks and Bash commands can post into their own session through `CLAUDE_CODE_MESSAGING_SOCKET` ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)). The safety model also helps here: a message "never counts as your consent", and slash commands inside a message arrive as plain text and do not run.

The limits are specific, and they matter for wb. **Sessions survive sleep but not shutdown.** After a reboot, sessions active in the last 48 hours show as failed and restart from their saved conversation when you reply. Running work does not carry on ([Agent view](https://code.claude.com/docs/en/agent-view.md)). The per-session OSC 7501 status protocol (v2.1.295+) **does not work inside tmux or for background sessions** ([Terminal config](https://code.claude.com/docs/en/terminal-config.md)), so a tmux status line still needs either hooks or a feed from `claude agents --json`. The files under `~/.claude/jobs/` are documented as "not a stable interface". There are three more platform details. On macOS a session can verify a hook's message only while the posting process is still alive, whereas Linux can verify it after the process exits. Posting from an outside script, such as a tmux keybinding, into a *different* session falls under normal inbound rules. And the JSON format for raw socket messages was not documented in the pages read ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)). For fan-out inside one task, **agent teams remain experimental**, with one team per session, no nesting, a fixed lead and no resume for in-process teammates ([Agent teams](https://code.claude.com/docs/en/agent-teams.md)). They suit short parallel bursts, not multi-day workers.

Paging away from the terminal is also native, with one condition. Remote Control drives local sessions from claude.ai/code or the phone app, sends push notifications ("Push when actions required", "Push when Claude decides"), and in server mode runs up to 32 sessions with optional per-session worktrees. It **requires a claude.ai Pro/Max/Team/Enterprise login and is disabled when `ANTHROPIC_API_KEY`, `apiKeyHelper` or a gateway is configured** ([Remote Control](https://code.claude.com/docs/en/remote-control.md)). Pushes cannot be configured per event. `CLAUDE_CLIENT_PRESENCE_FILE` suppresses them while you are at the machine. Remote Control is also what carries messages between machines, so the Mac and the Ubuntu box can only message each other if both are signed in through it. When it is blocked, ntfy works as a fallback. Self-hosted ntfy with `auth-default-access: deny-all` keeps message bodies on your own server. Its iOS upstream poll sends only a message ID and a hashed topic ([ntfy config](https://docs.ntfy.sh/config/)). On public ntfy.sh, topics are public by default ([ntfy privacy](https://docs.ntfy.sh/privacy/)).

## Third-party orchestrators duplicate native features rather than extend them

Among the terminal-native tools that run on both macOS and Ubuntu, **workmux** (MIT, worktree plus tmux window, status shown in window names, `merge` cleanup, a Zellij backend) ([workmux](https://github.com/raine/workmux)) and **agent-deck** (MIT, Go TUI on its own tmux socket, releases up to v1.7.21) ([agent-deck](https://github.com/asheshgoplani/agent-deck)) are the strongest. Claude Squad is popular, at about 8.7k stars. It is AGPL-3.0, and its FAQ suggests it breaks when the Claude CLI changes. Its README shows no needs-input indicator ([Claude Squad](https://github.com/smtg-ai/claude-squad)). ccmanager does without tmux and detects Waiting/Busy/Idle ([ccmanager](https://github.com/kbwo/ccmanager)). The GUI platforms are a poor fit. **Conductor is macOS-only** ([devtune.ai](https://devtune.ai/verticals/coding-agent-orchestration/conductor.md)). **Vibe Kanban's company shut down on 10 April 2026** and its remote features were removed after 30 days ([vibekanban.com](https://vibekanban.com/blog)). Opcode is no longer actively developed ([dev.to](https://dev.to/stravukarl/best-tools-for-managing-parallel-ai-coding-agents-in-2026-14l8)). The Vibe Kanban shutdown is a warning for a solo developer who wants a setup that lasts.

The core problem for wrappers is that they run Claude inside their own tmux sessions, beside Claude's supervisor, and **no source showed any wrapper reading agent-view state**. Adopting one would give you two session lists. Their remaining advantages are support for several agent CLIs (Codex, Gemini) and tighter tmux/nvim integration. Neither matters much for a Claude-only user. The one feature wb lacks and no native tool offers is agent-deck's **conductor**: a persistent agent session that watches child sessions, answers routine questions, escalates the rest, runs a 15-minute heartbeat, and keeps a `task-log.md` action log. It also forwards events to ntfy, Slack and Telegram ([agent-deck](https://github.com/asheshgoplani/agent-deck)). That is the nearest existing version of direction 7's foreman, and it is worth reading as a design reference even if you don't adopt it.

Practitioner reports set a ceiling on how much parallelism is useful. Users in one HN thread say **10 to 15 worktree sessions felt like "landing a plane all day"**. Parallel Opus agents **used up a Max plan in under an hour**, and 2 to 3 focused agents proved more reliable than 6 to 8 ([HN 47218318](https://news.ycombinator.com/item?id=47218318)). The same thread includes a user who rejected every orchestrator in favour of a custom tmux plus markdown-spec setup, the same choice wb made. For the attention problem specifically, the cleanest community design is **cekanje** (v0.2.0, May 2026). It is an HTTP-hook daemon that ties each `session_id` to a tmux pane, marks the session Waiting only when its pane is unfocused, clears it on `pane-focus-in`, and offers an fzf jump menu. It runs on macOS and Linux ([cekanje](https://docs.rs/cekanje/0.2.0)). Josh Morony's macOS recipe adds persistent alerts that are withdrawn when you focus the pane, and it warns that detecting "working" by scraping the TUI breaks easily ([joshmorony.com](https://www.joshmorony.com/effectively-manage-attention-across-multiple-coding-agents/)). On GNOME Wayland, **no source showed working click-to-focus**, so on Ubuntu plan for a notification plus a keyboard jump ([claude-tmux-hop](https://pypi.org/project/claude-tmux-hop/)).

## No native or third-party tracker replaces the markdown task store

Claude Code's own task layer is a working checklist, not a backlog. Setting `CLAUDE_CODE_TASK_LIST_ID` makes the to-do list persist under `~/.claude/tasks/<id>/` and shares it across sessions ([Interactive mode](https://code.claude.com/docs/en/interactive-mode.md)). But the lists are **not tied to a repo, use an internal format and work only with Claude Code** ([paddo.dev](https://paddo.dev/blog/from-beads-to-tasks/)), and anything under `~/.claude` is removed after `cleanupPeriodDays`, 30 days by default ([.claude directory](https://code.claude.com/docs/en/claude-directory)). Checkpoints (`/rewind`) track only Claude's file-tool edits. They skip changes made through Bash and symlinked files, which covers stow-managed dotfiles ([Checkpointing](https://code.claude.com/docs/en/checkpointing.md)). None of this can hold a multi-month, 360-task record.

**beads** (`bd`, now gastownhall/beads, v1.0 around April 2026) has the feature set closest to wb's. It has hierarchical epic IDs for parent/child families, `--claim` for atomic locks, `bd ready` for unblocked work, threaded message issues and LLM "memory decay" compaction ([beads](https://github.com/gastownhall/beads)). It also drew the most complaints. **It now stores data in embedded Dolt, a binary versioned SQL database that allows only one writer through a file lock.** JSONL is "an export… not the source of truth" ([beads](https://github.com/gastownhall/beads); [Beadbox](https://beadbox.app/en/blog/beads-v1-the-hard-way)). Users report constant idle disk activity, merge conflicts, git-hook interference and a failure on macOS repo paths that contain spaces ([HN 47772311](https://news.ycombinator.com/item?id=47772311); [tekai.dev](https://tekai.dev/references/2026-04-03-beads-graph-issue-tracker-ai-agents)). Its compaction also loses information, so it would gradually erase decision rationale. Adopting beads would give up wb's core property that the store is plain files you can grep. **beads_rust** keeps the older SQLite plus JSONL design with no daemon and no automatic git operations, but it has a single maintainer and needs a pinned Rust nightly to build ([beads_rust](https://github.com/Dicklesworthstone/beads_rust)).

**Backlog.md** is the closest drop-in. It stores one markdown file per task, with dependencies, milestones, separate decisions and docs areas, read-only archiving that keeps IDs and links, a terminal kanban, a local web board, `--json` output and an MCP server. It runs on macOS and Linux, and its store path is configurable ([Backlog.md](https://github.com/MrLesk/Backlog.md)). It shows no first-class handoff log, and the excerpt read did not show whether it has locking or subtasks, so wb's Handoffs and Follow-ups sections would end up in task bodies. For the decision shelf specifically, **seeds** (June 2026) is the right model rather than a tool to adopt. It tracks questions, alternatives and rationale, and requires a reason to resolve, defer or abandon anything. Its author built it because "plan files silently overwrote deliberation" ([jigsaw.io](https://jigsaw.io/tools/2026/06/10/introducing-seeds.html)). SaaS trackers (GitHub, Linear and Jira, all with official MCP servers) offer sub-issues, comment history and sync, but no `ready` semantics ([github-mcp-server](https://github.com/github/github-mcp-server)). For personal work they also put your records in a third-party account.

Across these tools, the useful pattern is a separation, not a product. Practitioners keep **mutable working memory apart from a permanent record**, and "pick one tracker and keep it boring" ([ANU COMP4020](https://comp.anu.edu.au/courses/comp4020-agentic-coding-studio/topics/task-tracking/)). Session-start "prime" hooks (`beans prime`, `bd prime`) re-inject tracker context at startup and before compaction, so resuming doesn't depend on the agent remembering ([beans](https://github.com/hmans/beans)). That supports direction 6. Handoffs and decisions belong in an append-only log that is never compacted. Status can be derived from that log, and an expiring backlog is just archiving, as Backlog.md does it, rather than summarising, as beads does it. wb's store is already closer to this design than any tool reviewed. It needs a prime hook and an append-only discipline, not a migration.

## The personal/employer boundary has to be built from git remotes and hooks

Claude Code has **no realm concept**. Everything it writes is plaintext under `~/.claude`, keyed by project path: full transcripts with every tool result, auto memory, prompt history, file snapshots, plans and tasks. The docs warn: "Anything that passes through a tool is written to a transcript on disk" ([.claude directory](https://code.claude.com/docs/en/claude-directory)). Auto memory is per repo and machine-local, and `autoMemoryDirectory` can move it from local settings ([Memory](https://code.claude.com/docs/en/memory)). The docs also say plainly that CLAUDE.md and memory are "context, not enforced configuration". To actually block something you need a `PreToolUse` hook ([Memory](https://code.claude.com/docs/en/memory); [Hooks](https://code.claude.com/docs/en/hooks)).

Git already provides the signal that direction 4 needs. **`includeIf "hasconfig:remote.*.url:..."` (Git 2.36+) chooses an identity by remote URL, wherever the clone sits on disk** ([git-config](https://git-scm.com/docs/git-config); [nite07](https://www.nite07.com/en/posts/git-includeif/)). One resolver script that answers "does this remote belong to the employer?" can drive commit identity, a `SessionStart` hook that injects realm context through `additionalContext`, and a `PreToolUse` guard on `Write|Edit` that denies writes into the other realm's store. No existing open-source tool does this; the research found none. It is a small custom build from documented parts. Physical separation does most of the work, though. Unlike the single-machine, two-account setups that most 2026 write-ups cover (which share skills through symlinks, and one of which even copies transcripts between accounts ([DEV](https://dev.to/daksh-gargas/one-brain-two-wallets-two-claude-code-accounts-on-one-machine-5ejb))), Jet's work transcripts only ever exist on the Ubuntu box. The resolver mainly guards against mistakes, such as a personal repo cloned onto the work machine or a skill writing employer content into a personal store.

Two leak paths deserve attention now. First, **claude.ai-synced skills are live on the Mac** (they are present under `~/.claude/skills/synced/`), and `syncClaudeAiSkills`/`syncClaudeAiPlugins: false` stops that sync on any machine that shouldn't receive them ([Settings](https://code.claude.com/docs/en/settings)). Second, skills such as compound-engineering write `docs/brainstorms/`, `docs/ideation/` and `reports/` into whatever repo is the current directory. In an employer repo, that output is employer content. On the dotfiles side, an allow-list sync of authored `~/.claude` files (`CLAUDE.md`, `rules/`, `skills/`, `agents/`, `settings.json`) is safer than an ignore list. Work-only config belongs in a separate private overlay repo cloned only on Ubuntu, either through stow packages or chezmoi externals ([chezmoi](https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/); [Larvitz](https://blog.hofstede.it/chezmoi-and-git-dotfiles-without-pretending-every-machine-is-the-same/)). The `ms-clients.sh` deletion in the current working tree suggests employer-specific scripts have been in the personal repo before. Its git history should be audited with gitleaks or `git log --all -- <path>`. Finally, the deciding factor is policy rather than tooling. Whether Remote Control, cross-machine messaging or personal plugins are allowed on the work machine depends on the employer's AI acceptable-use policy and on any managed settings (`forceLoginOrgUUID`, `strictKnownMarketplaces`), and managed settings override anything in the dotfiles ([Managed settings](https://code.claude.com/docs/en/managed-settings)).

## What to keep, replace and retire in wb

Retire **send-keys handoffs** outright. `SendMessage` delivers between tool calls, respects consent and needs no pane addressing. Replace **tmux-session-per-task and worktree creation** with `claude --bg --name <task>` and native worktree isolation. Keep only a `WorktreeCreate` hook if wb does environment setup beyond `.worktreeinclude`, and keep tmux for nvim and human shells. Replace most of the **hook-driven tmux status** with a status segment fed by `claude agents --json --all` for background sessions. Keep a thin hook layer, ideally in cekanje's style with focus-to-clear, only for foreground sessions inside tmux, where OSC 7501 does not work. Use the official `Notification` and `UserPromptSubmit` hooks rather than TUI scraping.

Keep the **360-file markdown store, its save/resume handoff sections and the decision-capture shelf**. Nothing researched does this better, and a store you can grep is the property worth protecting. Change how it is fed. A SessionStart prime hook injects the current task record on startup, resume and compaction. PostCompact and Stop hooks append drafts to a per-`session_id` handoff log (D3). An evening review promotes those drafts into the curated sections. Make handoffs and decisions append-only and never compacted, derive status from the log, and expire stale backlog by archiving rather than summarising (D6). Add a **realm resolver** that keys off the git remote and route task records through it (D4). Run direction 1 on the Mac now. The Ubuntu machine should keep its current wb until three things are checked: whether the work account allows Remote Control, whether it uses an API key or gateway, and what the AI acceptable-use policy says about transcripts and personal plugins. Since the remaining custom code is mostly hooks, consider packaging it as a Claude Code plugin with `hooks/hooks.json`, so the two machines install the same thing and the work overlay adds only realm config.

## Conclusion

The question for wb is no longer how to run and supervise many agents. Claude Code answered that natively in 2026, and the third-party market is repeating it. What wb should be from now on is a **memory and boundary layer**: the durable record of multi-day work and the rule about which realm a record belongs to. Those are the two things no vendor is positioned to own for a solo developer who works across a work machine and a personal one. That points to a much smaller wb, mostly hooks plus a markdown store, that depends on documented hook payloads instead of tmux internals and should therefore break less as Claude Code changes.

Two risks remain. Agent view is still a research preview, and a reboot ends running work, so dropping tmux persistence completely is premature for jobs that run overnight. The bigger unknown is the work machine. If the employer blocks Remote Control or routes Claude through a gateway, direction 5 and cross-machine messaging fall back to self-hosted ntfy and local-only coordination, and the Ubuntu setup will keep more of wb than the Mac. In both cases, practitioners' experience that 2 to 3 focused agents beat 6 to 8 suggests the right goal is clearer handoffs between a few sessions, not more sessions.
